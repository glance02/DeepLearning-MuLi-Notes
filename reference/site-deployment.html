01 / 一次更新，经过哪些地方？

你已经有一组 HTML、CSS 和 JavaScript 文件。练习里的计算在浏览器中进行；服务器提供这些文件。Markdown 笔记则先经过 Python 脚本，生成浏览器可以阅读的 HTML。

本地修改→commit、push→GitHub main→服务器 pull
生成 HTML→检查链接→切换 current→浏览器刷新
名词这次指什么负责什么
源文件仓库里的笔记、页面和脚本供你编辑，保存内容与生成规则
构建运行 build_site.py选取内容、生成网页、改写链接、检查输出
发布版本releases/ 下的一份完整输出保存某次构建的网页和附件
软链接记录目标路径的文件系统入口让固定路径指向一个发布版本
Nginx服务器现有的 Web 服务接收 HTTPS 请求，读取对应的站点文件
定时任务systemd timer 触发 service每天启动一次更新程序

先记住各自的职责。软链接不会去 GitHub 拉代码；定时任务负责启动更新，Git 负责获取提交。

这次先读本地页面和引用关系，确认要带哪些资源。随后通过 ssh-manager，一次执行一条用途明确的检查命令，用事实决定接入方式。

检查实际发现决定
页面和脚本现有练习使用浏览器 JavaScript按静态文件发布
域名解析glance02.xyz 指向 myserver直接接入该服务器

仓库可达性直连 GitHub 超时，现有本机代理可以访问为这个仓库和更新任务设置代理

例如 ss -ltnp 观察监听端口；读取 Nginx 配置找网站根目录；git ls-remote 检查能否读到远程分支。这些动作收集证据，尚不发布内容。

03 / 保存、提交、推送、拉取

这四个动作发生在不同位置。保存让文件写入本地磁盘；commit 把选定修改记为本地版本；push 把提交发送到 GitHub；服务器 pull 才更新服务器的工作区。

你的电脑                  GitHub                  服务器
修改 → 保存 → commit  ──push──→ main ──pull──→ repo/
                                                ↓
                                            下一步：构建

因此，只在 VS Code 保存文件，服务器明天仍读不到这份新修改。即使已经 push，网站也要等下一次更新任务完成，或由你手动触发。

更新程序使用 git pull --ff-only origin main。它只允许快进更新；分支历史发生分叉时会失败。脚本还会先检查工作区是否有本地修改，避免直接覆盖服务器上的改动。

命令原理：Git 官方：git pull 与 --ff-only · 实现：update_site.py 的 update()

04 / 源文件怎样变成可访问的网站？

build_site.py 读取手边册、练习和斋藤笔记。现有 HTML 保留结构，Markdown 经过转换，再加上统一的页面外壳、章节导航和样式。

  1. 选内容：选定的页面和笔记进入网站；发布页面引用的 PDF、代码、Notebook 和图片也按规则带上。
  2. 生成 HTML：Python-Markdown 处理表格和代码块；Arithmatex 保留数学表达，再由浏览器中的 MathJax 显示公式。
  3. 整理链接：已发布笔记的 .md 链接变成 .html；范围外内容转到 GitHub。
  4. 检查输出：确认站内文件和 HTML 锚点存在，生成 build.json 记录提交号与检查结果。

为什么保留目录层级？

当前网页：/deep-learning/lessons/0001-array-shapes.html
样式链接：../assets/teach.css
解析结果：/deep-learning/assets/teach.css

页面里的 ../ 表示回到上一层。保持 lessons、assets、reference 的相对位置，原有引用就能继续使用。PDF 后的 #page=39 也会保留，交给阅读器定位。

venv 又是什么？

构建用的 Python 包装在独立虚拟环境中。服务器通过 /srv/deep-learning/venv/bin/python 明确选择这个环境，固定版本记录在 deploy/requirements.txt。虚拟环境可以重新创建，笔记和脚本保存在仓库里。

Python-Markdown 扩展 · Arithmatex 公式转换 · Python 官方 venv

05 / 软链接让固定入口指向新版本

/srv/deep-learning/
├── repo/             Git 工作区：保存源文件
├── venv/             构建所用的 Python 环境
├── releases/
│   ├── 版本 A/       上一次生成的完整网站
│   └── 版本 B/       新生成的完整网站
├── previous → releases/版本 A/
└── current  → releases/版本 B/

/var/www/myhtml/deep-learning
    → /srv/deep-learning/current
    → /srv/deep-learning/releases/版本 B/

访问者使用的路径始终相同。发布程序先在新目录完成构建和校验，再将 current 切向新目录。构建阶段失败时，会清理本次候选目录，保留现有入口。

atomic_link() 先在同一父目录创建临时软链接，再用 os.replace() 替换入口。这个入口替换是原子的，避免先删除入口、再创建入口之间的空档。它针对入口这一项操作；已经开始读取旧版的请求仍可能使用旧文件。

保留的 previous 用于回退。回退后，下次正常更新仍以 GitHub 的 main 为发布目标。

实现：publish()、atomic_link() 与 --rollback · 原理：Python 官方 os.replace

06 / 域名后面的路径怎样找到文件？

浏览器先通过域名找到服务器，再向现有 HTTPS 站点请求路径。这个站点的根目录是 /var/www/myhtml。Nginx 将请求路径映射到根目录下面，Linux 沿软链接找到实际文件。

请求： https://glance02.xyz/deep-learning/reference/index.html
映射： /var/www/myhtml/deep-learning/reference/index.html
解析： /srv/deep-learning/current/reference/index.html
读取： 当前发布版本中的 reference/index.html

两个入口 /deep-learning 和 /deep-learning/ 会返回 302，跳到手边册的实际地址。这样从首页继续访问相对链接时，浏览器知道页面位于哪一层目录。

展开看这次的路径配置
location = /deep-learning {
    return 302 /deep-learning/reference/index.html;
}

location = /deep-learning/ {
    return 302 /deep-learning/reference/index.html;
}

location ^~ /deep-learning/ {
    try_files $uri $uri/ =404;
    add_header Cache-Control "no-cache";
}

这段配置被包含在现有 HTTPS server 块中，继承原来的根目录和证书。no-cache 允许缓存，但要求复用缓存前向服务器重新确认。

首次接入时备份配置，通过 nginx -t 后才 reload。后续只改网页内容、切换软链接时，通常不需要 reload。

Nginx 官方：静态内容与 reload · HTTP 标准：no-cache · 本项目路径配置

07 / timer 决定何时，service 决定做什么

文件关键内容含义
deep-learning-update.timerOnCalendar=*-*-* 04:00:00 Asia/Shanghai每天北京时间 04:00 触发
同一个 timerPersistent=true停机错过日程后，恢复时可补跑一次
deep-learning-update.serviceType=oneshot每次启动执行一次更新程序
同一个 serviceUser=deep-learning用专用部署用户执行

服务启动 update_site.py：先拉取，再比较提交号。当前 build.json 已记录相同提交时直接跳过；有新提交则生成新版并切换入口。更新过程会写入 systemd 日志。

Git 仓库的代理设置保存在该仓库配置中；service 中也设置了构建所需的代理环境变量。它们影响更新过程，访问者读已发布网页时无需经过这个 GitHub 代理。

systemd 官方：timer 与 Persistent · 项目 service · 项目 timer

08 / 这次真正遇到的错误

排错的顺序是：写下观察到的现象，找能区分原因的检查，依据结果修改，再验证原来的问题是否消失。

现象检查得到的证据处理
服务器读 GitHub 超时使用现有本机代理后，能读到 main 的提交号给仓库与更新任务配置该代理
服务器创建 venv 失败错误提示缺少 ensurepip／venv 支持安装 python3.12-venv，再创建环境
新站点文件返回 404namei -l 显示发布目录是 0700；Nginx 日志出现 Permission denied发布前设为 0755，并加入 Linux 权限测试
构建报告的文件数偏少最初按 *.* 统计，漏掉 LICENSE，也未计入即将写出的报告遍历所有文件，计入报告自身，并核对数量
自动浏览器工具停止工具报告无法可靠识别当前 URL；你随后提供了正常网页截图停止 UI 自动操作，继续 HTTP 验收，记录验证范围

为什么文件明明存在，还会 404？

Python 的 mkdtemp() 在 Linux 上创建的目录默认只允许创建者访问。这次创建者是部署用户，Nginx worker 使用另一个用户；访问路径时必须能逐层穿过目录。配置中的 try_files 最终返回 404，所以要结合错误日志判断原因。

0700 → 所有者 rwx；组 ---；其他人 ---
0755 → 所有者 rwx；组 r-x；其他人 r-x

目录的 x：允许沿路径查找其中的条目
文件的 r：允许读取文件内容

这次修复的是生成目录的访问权限，并在后续发布时自动设置；文件仍由部署用户管理。可以在 publish() 中找到 candidate.chmod(0o755)。

Python 官方 mkdtemp · Linux 官方手册：路径查找权限
